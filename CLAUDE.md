## Conventions

### File naming

- Resource directories: kebab-case matching the API path segment (`partner-fees`, `virtual-accounts`, `bank-accounts`).
- Single-file resources inside a directory: `index.ts`.
- Grouped resources without their own parent: individual files (`wallets/blockchain.ts`, `wallets/custodial.ts`).
- Sub-resource files: placed inside the parent resource directory (`payins/quotes.ts`).
- Tests: `{resource-name}.test.ts` colocated next to the resource file.

### Type naming

All types are defined in the same file as the factory function, above it. Naming pattern:

| Pattern | Example |
|---|---|
| Entity type | `Payin`, `Payout`, `CustodialWallet` |
| List input | `ListPayinsInput` |
| List response | `ListPayinsResponse` |
| Create input | `CreatePayinInput`, `CreatePartnerFeeInput` |
| Create response | `CreatePartnerFeeResponse` |
| Get input | `GetPayinInput` |
| Get response | `GetPayinResponse` |
| Update input | `UpdateCustomerInput` |
| Delete input | `DeleteCustomerInput` |
| String-only IDs | `export type GetPayinInput = string;` |
| Object inputs | `export type CreatePayoutInput = { ... };` |

Types use `snake_case` field names matching the API JSON exactly. Never camelCase.

### Factory function naming

```
create{PascalResourceName}Resource
```

Examples: `createPayinsResource`, `createPartnerFeesResource`, `createBlockchainWalletsResource`.

### Method naming

| HTTP operation | Method name |
|---|---|
| GET list | `list` |
| GET single | `get` |
| POST create | `create` |
| PUT update | `update` |
| DELETE | `delete` |
| Custom action | Descriptive camelCase: `getTrack`, `createEvm`, `submitDocuments`, `getLimits` |

### Import style

- Always use `import type` for type-only imports (enforced by biome `useImportType`).
- Shared types come from `../../../types` (the `types/index.d.ts` file).
- Internal API client: `import type { InternalApiClient } from "../../internal/api-client";`
- Query strings: `import { toQueryString } from "../../internal/query";` (never `new URLSearchParams(params)` on an input object: it sends unset filters as the text `"undefined"`).
- Path depth depends on file location. Resources at `src/resources/{name}/index.ts` use `../../internal/...` and `../../../types`.

### Code style

- Comments ship: JSDoc ends up in `dist/*.d.ts` and IDE hovers. Never cite internal plans, ledgers, other repos' file paths or local paths in them (the Package workflow fails on `sdk-parity`, `blindpay-v2` or `/Users/` in the tarball).
- Every optional option property is typed `?: T | undefined`, so consumers on `exactOptionalPropertyTypes` can pass an unset env value (`test/consumer-types/exact-optional.mts`).
- Every README ```typescript block must compile on its own as an ES module (it may use the `blindpay` client from Configuration): `bun run check-consumer-types`.

- Formatter: 4-space indent, double quotes, trailing commas (ES5), semicolons always, LF line endings, 100-char line width.
- Linter: Biome recommended rules. No unused variables (error). `import type` required (error). No explicit `any` (warn).
- TypeScript: `verbatimModuleSyntax: true` (must use `import type` for type-only imports). `strict: true`.

## Transport (`src/internal/http.ts`)

Every request, JSON or multipart, goes through `send()`; resources never call `fetch`. It owns:

- **Config** (`BlindPayOptions`): `baseUrl` (default `https://api.blindpay.com`; the host only, since paths start `/v1`: trailing `/` and one trailing `/v1` are dropped by `normalizeBaseUrl`), `timeoutMs` (60 s per attempt, body read included), `maxRetries` (2), `fetch` (injectable; tests pass a fake one).
- **Idempotency**: an `idempotencyKey` that is empty, longer than 255 characters or not equal to its trimmed form, or an `Idempotency-Key` in `options.headers` (any casing), is rejected with `type: "invalid_request"` before anything is sent. Per-call headers named `Authorization`, `User-Agent`, `Accept` or `Content-Type` (any casing) are dropped. With retries on, a non-multipart mutation without a key gets a `randomUUID()` key **before the first attempt**. Multipart never sends one.
- **Attempts**: a `fetch()` failure is "no response"; once the status line has arrived, a failure while reading the body is judged by that status (A2), so a 5xx mutation is never resent and a 2xx whose body can't be read is an `invalid_response` error, not a retry.
- **Retries** follow the sdk-parity Appendix A2 table in `decide()`, which also sets `error.retryable`, so the two can't drift. GETs: no response, 408, 429, 500/502/503/504. Mutations: only no response, 429 and `409 idempotency_key_in_flight`, and **never a 5xx** (the API releases the key on a 5xx, so a resend re-executes). `Retry-After` is honoured when it is an integer of at most 60 s; otherwise `min(8 s, 0.5 s * 2^attempt)` with jitter. Rows 2-3 come first: a multipart or unkeyed mutation is never `retryable`, whatever the status. The body is serialised once. Jitter comes from `node:crypto` `randomInt`. Sleeps stop on the caller's `signal`, returning an `aborted` error (status 0) that keeps the `idempotency_key` and the earlier failure's `retryable`, so the call can be resumed. A per-call `timeoutMs` that isn't positive is rejected.
- **Errors** never throw: an API error envelope always yields `errors` (`[]` when the body has none), and `ErrorResponse` gains `status` (0 without a response), `request_id` (`X-Request-Id`), `idempotency_key`, `retryable`, `type` and `retry_class`, each set only when known. `retry_class` is set only when the error has a `code`: the catalogue's class from `src/error-codes.ts`, or `unknown` for a code the catalogue doesn't list; network, timeout and other code-less errors don't get the key. It never feeds `decide()`. A non-JSON error body becomes `HTTP <status> <text>`.
- `Content-Type: application/json` only when there is a body.
- **Secrets** (sdk-parity C13): the transport config, which holds the API key, lives in the client's ECMAScript-private `#transport`, and `BlindPay` defines `toJSON()` / `util.inspect.custom` returning the configuration with `apiKey: "[redacted]"`. Never store the key on a normal property or a resource, and never put it, or a request body, in an error message. A transport error message never carries a URL query string (`messageOf` strips it: list filters such as `customer_name` are personal data), and a webhook verification error never carries the secret. `src/client-secrets.test.ts` checks inspect (with `showHidden`), `JSON.stringify` and error results.

Retry tests use `vi.useFakeTimers({ toFake: ["setTimeout", "clearTimeout"] })`; never let a test sleep for real. A client in a test that mocks a 5xx GET and doesn't test retries should pass `maxRetries: 0`.

## Webhooks (`src/webhooks.ts`)

Verification uses the official `svix` package for the HMAC (sdk-parity D20): `verifySignature` checks the headers and the timestamp against `options.tolerance` (seconds, default 300; svix's own `verify` hard-codes 5 minutes), signs with svix's `sign` and compares each `v1,` signature in constant time. The standalone `verifyWebhook(payload, headers, secret, options?)` (never throws) and `constructWebhookEvent(payload, headers, secret, options?)` (throws `BlindPayError`) need no client; the client's `verifyWebhookSignature` / `constructWebhookEvent` methods delegate to them and keep their old signatures and return types. The standalone `constructWebhookEvent` returns an event this SDK doesn't know as `UnknownWebhookEvent` (`{ webhook_event, raw }`); callers check `isUnknownWebhookEvent` before a `switch`. Never add a `string` member to the `WebhookEvent` union: it would stop the switch from narrowing.

When a webhook event is added to the `WebhookEvents` union, add it to `src/internal/webhook-event-names.ts` too (a type test fails otherwise). The 14 vectors in `test/fixtures/webhook-vectors.json` run twice: with only `Date` faked (`vi.useFakeTimers({ toFake: ["Date"] })` + `vi.setSystemTime`), and on real timers through the injectable clock `options.now` (a `Date` or Unix **seconds**, the unit of `svix-timestamp`).

## Generate before you hand-write

`scripts/api-sync/` is a deterministic patcher (no LLM) that reconciles the SDK against the OpenAPI spec. Anything it can produce must come from it, not from a hand-written (or model-written) edit:

```bash
bun run sync -- --spec /tmp/openapi.public.json   # apply against the current public spec (built below)
bun run sync:check                                # CI gate against the committed snapshot
bun run audit:types                               # informational full type audit
```

`.api-sync/spec-snapshot.json` is the spec the SDK last synced to, so applying against it only restores methods the SDK lost. To pick up a new endpoint, build the current public spec from blindpay-v2's committed `openapi.json` with blindpay-v2's own public filter (run inside a blindpay-v2 checkout):

```bash
git fetch origin main
mkdir -p /tmp/v2 && git archive origin/main apps/api/openapi.json apps/api/src/shared/helpers scripts/openapi-public-filter.ts | tar -x -C /tmp/v2
(cd /tmp/v2 && bun scripts/openapi-public-filter.ts --in apps/api/openapi.json --out /tmp/openapi.public.json)
```

Normally the api-sync workflow does this for you: blindpay-v2's `sdk-sync.yml` delivers the spec and dispatches the run. A successful `--apply` also refreshes the snapshot, written as 2-space JSON with a trailing newline (`formatSnapshot`), so a refresh is a small diff even when the delivered spec is minified.

It applies three kinds of change on its own: new enum members, new optional fields, and new methods for standard operations on an existing resource (instance-scoped path, JSON request and response, an existing `create{X}Resource(instanceId, client)` factory). For anything else it prints the exact reason it stopped. Only then use the manual recipes below: a brand-new resource, non-instance paths (`/available/*`, `/e/*`), multipart uploads, non-GET operations with query parameters, and resource files with a non-standard factory. After a manual change, `bun run sync:check` names any `.api-sync/spec-map.json` entry still missing.

It also owns `src/error-codes.ts`: `--apply` regenerates it from the table in the spec's `Errors` tag (`scripts/api-sync/error-codes.ts`), and `--check` fails while it is stale, so a code the API adds fails CI until it is synced. A code that disappears from the spec is a removal and needs a human. Never edit the file by hand. An `ErrorResponse` with a `code` carries `retry_class` from that catalogue (`unknown` for an uncatalogued code); it never feeds the retry decision in `decide()`.

A type may share fields through a same-file base joined with `&` (`BankAccountCreateCommon & { ... }`, `PayoutSourceWallet & { ... }`): api-sync resolves those fields (`extractResolvedFields` in `sdk-scan.ts`). A base from another file is not resolved, so keep shared bases next to their users.

Webhook payload schemas typed as `{ webhook_event } & X` sit in `spec-map.json`'s `ignore.schemas` with `sameShapeAs: "<X's schema>"`; sync:check fails (needs-human) when such a webhook schema stops having exactly that schema's properties and required list (`scripts/api-sync/webhook-shapes.ts`), so drift on a webhook alone is never silent.

Deliberate differences from the spec are recorded in `.api-sync/unmodeled.json` with an owner and a reason. Never silence a finding by editing that file without the reason being true.

## How to: Add a New Resource

### Step 1: Create the resource file

Create `src/resources/{resource-name}/index.ts`.

Template for a standard instance-scoped resource:

```typescript
import type {
    BlindpayApiResponse,
    PaginationMetadata,
    PaginationParams,
    RequestOptions,
    SuccessResponse,
} from "../../../types";
import type { InternalApiClient } from "../../internal/api-client";
import { toQueryString } from "../../internal/query";

// -- Entity type --
export type Widget = {
    id: string;
    name: string;
    instance_id: string;
    created_at: string;
    updated_at: string;
};

// -- Input/Output types --
export type ListWidgetsInput = PaginationParams & {
    status?: string;
};

export type ListWidgetsResponse = {
    data: Widget[];
    pagination: PaginationMetadata;
};

export type CreateWidgetInput = {
    name: string;
    description?: string | null;
};

export type CreateWidgetResponse = {
    id: string;
};

export type GetWidgetInput = string;

export type GetWidgetResponse = Widget;

export type UpdateWidgetInput = {
    widget_id: string;
    name?: string;
};

export type DeleteWidgetInput = string;

// -- Factory function --
export function createWidgetsResource(instanceId: string, client: InternalApiClient) {
    return {
        list(
            params?: ListWidgetsInput,
            options?: RequestOptions
        ): Promise<BlindpayApiResponse<ListWidgetsResponse>> {
            return client.get(`/instances/${instanceId}/widgets${toQueryString(params)}`, options);
        },
        create(
            { ...data }: CreateWidgetInput,
            options?: RequestOptions
        ): Promise<BlindpayApiResponse<CreateWidgetResponse>> {
            return client.post(`/instances/${instanceId}/widgets`, data, options);
        },
        get(
            id: GetWidgetInput,
            options?: RequestOptions
        ): Promise<BlindpayApiResponse<GetWidgetResponse>> {
            return client.get(
                `/instances/${instanceId}/widgets/${encodeURIComponent(id)}`,
                options
            );
        },
        update(
            { widget_id, ...data }: UpdateWidgetInput,
            options?: RequestOptions
        ): Promise<BlindpayApiResponse<SuccessResponse>> {
            return client.put(
                `/instances/${instanceId}/widgets/${encodeURIComponent(widget_id)}`,
                data,
                options
            );
        },
        delete(
            id: DeleteWidgetInput,
            options?: RequestOptions
        ): Promise<BlindpayApiResponse<SuccessResponse>> {
            return client.delete(
                `/instances/${instanceId}/widgets/${encodeURIComponent(id)}`,
                options
            );
        },
    };
}
```

For a resource NOT scoped to an instance (like `available`), omit `instanceId` from the factory signature:

```typescript
export function createAvailableResource(client: InternalApiClient) {
    return {
        getRails(options?: RequestOptions): Promise<BlindpayApiResponse<GetRailsResponse>> {
            return client.get("/available/rails", options);
        },
    };
}
```

### Step 2: Register in `src/client.ts`

1. Add the import at the top:
```typescript
import { createWidgetsResource } from "./resources/widgets";
```

2. Add the property declaration to the `BlindPay` class:
```typescript
readonly widgets: ReturnType<typeof createWidgetsResource>;
```

3. Initialize in the constructor body:
```typescript
this.widgets = createWidgetsResource(this.instanceId, this.api);
```

### Step 3: Re-export from `src/index.ts`

Add one line:
```typescript
export * from "./resources/widgets";
```

## How to: Add a Method to an Existing Resource

### Step 1: Add types to the resource file

Add the input and response types above the factory function in the resource's `index.ts`:

```typescript
export type ActivateWidgetInput = string;

export type ActivateWidgetResponse = {
    id: string;
    status: string;
};
```

### Step 2: Add the method inside the factory function's return object

```typescript
export function createWidgetsResource(instanceId: string, client: InternalApiClient) {
    return {
        // ... existing methods ...
        activate(
            id: ActivateWidgetInput,
            options?: RequestOptions
        ): Promise<BlindpayApiResponse<ActivateWidgetResponse>> {
            return client.post(
                `/instances/${instanceId}/widgets/${encodeURIComponent(id)}/activate`,
                {},
                options
            );
        },
    };
}
```

### Step 3: Add tests and a changeset

Follow the same test pattern. Add a `minor` changeset (a new method is a new feature).

## How to: Modify Types

### Add a field to an existing type

Add the field directly to the type definition. Use `snake_case`. Match the API response exactly.

```typescript
export type Widget = {
    id: string;
    name: string;
    description: string | null;  // <-- new field
    instance_id: string;
    created_at: string;
    updated_at: string;
};
```

If the field is optional in the API response, use `?`:
```typescript
    metadata?: Record<string, string> | null;
```

### Remove a field

Delete the field from the type definition. Search the codebase for any usage of that field.

### Rename a field

Change the field name in the type definition. This is a breaking change -- use a `major` changeset.

### Shared types

Types like `Currency`, `Network`, `StablecoinToken`, `TransactionStatus`, `PaginationParams`, `PaginationMetadata`, `BlindpayApiResponse`, and `Country` live in `types/index.d.ts`. If a new enum value needs to be added to a shared type (e.g., a new network), edit it there. `src/index.ts` re-exports them with an explicit `export type { ... } from "../types"` list (type-only, so esbuild never tries to load the `.d.ts` at runtime). When a resource starts using a new shared type, add it to that list; never re-export the whole file, so dead or stale types (e.g. `PayoutForcedProvider`) don't become public API. `src/index.test.ts` asserts what the entry exports and what it must not.

## Deferred to the next major

The repo's semver rules make widening or narrowing a response type a major change, so these known gaps stay as released, documented on the type and listed in `src/internal/fixture-divergences.ts` (reason `NEXT MAJOR`):

- Fields the API never sends but the type requires: `Payout.tracking_partner_fee` (`@deprecated`), `customer_id` on the payout create responses, `is_tos_accepted` on `customers.list` and the customer webhooks, `has_virtual_account` on `payouts.list`.
- Fields the API can omit: payin `tracking_transaction.external_id`, transfer `tracking_*.error_message`, a development instance's virtual-account `blockchain_wallet`.
- `virtualAccounts.get` answers an unknown id with `200 null`: `data` should be nullable.
- Narrowings the spec allows (node audit 9.10): `Transfer.status` without `on_hold`, required tracking fields on the EVM and Stellar payout create responses.
- Removals: the `@deprecated` fields and types (`forced_provider`, `provider_integration`, fees `yield.partner_wallet_address`, `CreatePayoutInput`, `offset`), and `UpdateInstanceMemberRoleInput` to snake_case.

## How to: Remove a Resource

1. Delete the resource directory: `src/resources/{resource-name}/`.
2. Remove the import from `src/client.ts`.
3. Remove the property declaration from the `BlindPay` class.
4. Remove the initialization line from the constructor.
5. Remove the re-export line from `src/index.ts`.
6. Create a `major` changeset (breaking change).

## How to: Add a Sub-Resource

A sub-resource is nested under a parent on the client (e.g., `blindpay.payins.quotes`, `blindpay.instances.webhookEndpoints`).

### Step 1: Create the sub-resource file

Place it inside the parent resource directory. For a sub-resource of `payins`:

File: `src/resources/payins/quotes.ts`

```typescript
import type { BlindpayApiResponse, RequestOptions } from "../../../types";
import type { InternalApiClient } from "../../internal/api-client";

export type CreatePayinQuoteInput = {
    blockchain_wallet_id: string;
    // ...
};

export type CreatePayinQuoteResponse = {
    id: string;
    // ...
};

export function createPayinQuotesResource(instanceId: string, client: InternalApiClient) {
    return {
        create(
            { ...data }: CreatePayinQuoteInput,
            options?: RequestOptions
        ): Promise<BlindpayApiResponse<CreatePayinQuoteResponse>> {
            return client.post(`/instances/${instanceId}/payin-quotes`, data, options);
        },
    };
}
```

### Step 2: Register in `src/client.ts`

1. Import:
```typescript
import { createPayinQuotesResource } from "./resources/payins/quotes";
```

2. Declare the type with intersection:
```typescript
readonly payins: ReturnType<typeof createPayinsResource> & {
    quotes: ReturnType<typeof createPayinQuotesResource>;
};
```

3. Initialize with spread:
```typescript
this.payins = {
    ...createPayinsResource(this.instanceId, this.api),
    quotes: createPayinQuotesResource(this.instanceId, this.api),
};
```

### Step 3: Re-export from `src/index.ts`

```typescript
export * from "./resources/payins/quotes";
```

### Grouped resources (no parent entity)

For groupings like `wallets` where there is no parent `createWalletsResource`, each sub-resource is its own file and the parent is a plain object:

```typescript
// Declaration
readonly wallets: {
    blockchain: ReturnType<typeof createBlockchainWalletsResource>;
    offramp: ReturnType<typeof createOfframpWalletsResource>;
    custodial: ReturnType<typeof createCustodialWalletsResource>;
};

// Initialization
this.wallets = {
    blockchain: createBlockchainWalletsResource(this.instanceId, this.api),
    offramp: createOfframpWalletsResource(this.instanceId, this.api),
```

## Testing

### Framework

Vitest with `vitest-fetch-mock`. The `fetchMock` global is available in all test files (configured in `vitest.setup.mts`). Vitest globals (`describe`, `it`, `expect`, `afterEach`) are enabled.

### Test file location

Colocated with the resource file:
- `src/resources/payins/payins.test.ts` for `src/resources/payins/index.ts`
- `src/resources/wallets/blockchain.test.ts` for `src/resources/wallets/blockchain.ts`

### Test pattern

```typescript
import { afterEach, describe, expect, it } from "vitest";
import { BlindPay } from "../../client";
import type { ListWidgetsResponse } from ".";

describe("Widgets", () => {
    afterEach(() => fetchMock.resetMocks());

    const blindpay = new BlindPay({ apiKey: "test-key", instanceId: "in_000000000000" });

    describe("List widgets", () => {
        it("should list widgets", async () => {
            const mockedResponse: ListWidgetsResponse = { /* ... */ };

            fetchMock.mockResponseOnce(JSON.stringify(mockedResponse), {
                headers: { "Content-Type": "application/json" },
            });

            const { data, error } = await blindpay.widgets.list();

            expect(error).toBeNull();
            expect(data).toEqual(mockedResponse);
        });
    });
});
```

Key rules:
- Always call `fetchMock.resetMocks()` in `afterEach`.
- Instantiate `BlindPay` with `apiKey: "test-key"` and `instanceId: "in_000000000000"`.
- Use `fetchMock.mockResponseOnce` with `JSON.stringify` and content-type header.
- Destructure `{ data, error }` from the result.
- Assert `error` is null and `data` matches the mock.

### Spec fixtures and response types

`src/internal/test-operations.ts` lists every spec operation with the client method(s) that implement it; add a row with every new method. Two tests run over it: `fixture-round-trip.test.ts` (method, path and every fixture variant through the transport) and `fixture-types.test.ts`, which type-checks every `full`, `required_only`, `nullables_null` and `decimals` variant (responses and webhooks) against the method's declared response type with the repo's tsconfig. When it reports a type error, check the API source (blindpay-v2) before touching the type: a field the API never sends is made optional (and `@deprecated` if it was dropped); a field the handler always sends, or one that can be omitted but whose widening would break callers, goes into `src/internal/fixture-divergences.ts` with the reason. Entries that stop matching a real difference fail the test.

## Versioning

This project uses [Changesets](https://github.com/changesets/changesets).

### Semantic versioning rules

- `patch`: Bug fixes and type corrections that add nothing new to the public API.
- `minor`: New resources, new methods on existing resources, new sub-resources, new exports, new optional fields on existing types, new enum members. api-sync's `classifyBump` follows the same rule: anything it applies is a minor.
- `major`: Removing resources/methods, renaming fields, removing fields, changing required/optional status of input fields, adding `| null` to a response field, narrowing a response field from `string` to a union, removing an enum member.

### Creating a changeset

```bash
bunx changeset
```

Or manually create `.changeset/{name}.md`:

```markdown
---
"@blindpay/node": minor
---

Added widgets resource with CRUD methods.
```

The changeset file name should be a random short identifier (changesets CLI generates these automatically).

### Configuration

- `baseBranch`: `main`
- `access`: `public` (npm)
- `commit`: `false` (changesets do not auto-commit)
- `changelog`: `@changesets/changelog-github` (links PRs and authors in `CHANGELOG.md`)

### Releasing

`.github/workflows/publish.yaml` runs the [Changesets release flow](https://changesets.dev/guide/automating) on every push to `main`:

1. Changesets pending: open or update the `chore(release): version packages` PR. It bumps `package.json`, writes `CHANGELOG.md` and deletes the consumed changesets.
2. That PR merged: type-check, test, build and pack, then publish to npm with trusted publishing (OIDC, no npm token), tag `vX.Y.Z` and create the GitHub release.

Rules:
- Never edit `version` in `package.json` by hand, and never run `changeset version` or `changeset publish` locally. A merge without a changeset releases nothing.
- api-sync PRs write `.changeset/api-sync-<spec sha>.md` instead of bumping the version, so they release through the same Version Packages PR.
- Keep the workflow file name `publish.yaml`: npm's trusted publisher is bound to it.
- A stuck or failed Publish run is re-run with `workflow_dispatch` on `main` (Actions, then Publish, then Run workflow). [`RELEASING.md`](RELEASING.md) is the runbook: secrets, re-runs, verifying the published artifact, known traps.

## OpenAPI to SDK Mapping Rules

This section defines exactly how an OpenAPI specification maps to SDK code.

### Path to resource mapping

| API path pattern | Resource location | Factory function |
|---|---|---|
| `/instances/{id}/widgets` | `src/resources/widgets/index.ts` | `createWidgetsResource` |
| `/instances/{id}/widgets/{widgetId}` | Same file as above | Same factory, different method |
| `/instances/{id}/widgets/{widgetId}/actions` | Same file if simple | Method in same factory |
| `/available/something` | `src/resources/available/index.ts` | `createAvailableResource` (no instanceId) |
| `/instances/{id}/parent/{parentId}/children` | `src/resources/children/index.ts` OR `src/resources/parent/children.ts` | `createChildrenResource` |
| `/e/widgets/{id}` | Same widget resource file | Method like `getTrack` (public/external endpoints) |

### HTTP method to SDK method mapping

| HTTP method | Path pattern | SDK method name | Notes |
|---|---|---|---|
| `GET` | `/instances/{id}/widgets` | `list` | Returns paginated response |
| `GET` | `/instances/{id}/widgets/{widgetId}` | `get` | Input is a string ID |
| `POST` | `/instances/{id}/widgets` | `create` | Input is an object |
| `PUT` | `/instances/{id}/widgets/{widgetId}` | `update` | Input destructures ID from body |
| `PATCH` | `/instances/{id}/widgets/{widgetId}` | `update` | Same pattern as PUT |
| `DELETE` | `/instances/{id}/widgets/{widgetId}` | `delete` | Input is a string ID |
| `POST` | `/instances/{id}/widgets/{widgetId}/action-name` | `actionName` | camelCase the action |
| `GET` | `/instances/{id}/widgets/{widgetId}/sub-thing` | `getSubThing` | camelCase with get prefix |

### Request body to input type mapping

OpenAPI request body schema fields map 1:1 to TypeScript type fields using `snake_case`:

```yaml
# OpenAPI
requestBody:
  content:
    application/json:
      schema:
        type: object
        required: [name, currency]
        properties:
          name:
            type: string
          currency:
            type: string
            enum: [USD, BRL, MXN]
          description:
            type: string
            nullable: true
```

Maps to:

```typescript
export type CreateWidgetInput = {
    name: string;
    currency: "USD" | "BRL" | "MXN";
    description?: string | null;
};
```

Rules:
- Required fields: no `?`.
- Optional fields: use `?`.
- Nullable fields (`type: [..., "null"]` in the spec): add `| null`, on inputs and responses alike. `sync:check` fails on a spec-nullable field whose SDK type has no `| null`.
- String enums: use union literal types.
- Numbers: use `number`.
- Booleans: use `boolean`.
- Arrays: use `Array<T>` or `T[]`.
- Nested objects: inline or define a separate type.
- Date strings: use `string`.

### Response schema to output type mapping

Response schemas map the same way. Every field from the API response becomes a type field:

```yaml
# OpenAPI
responses:
  200:
    content:
      application/json:
        schema:
          type: object
          properties:
            id:
              type: string
            status:
              type: string
              enum: [processing, completed, failed]
            created_at:
              type: string
              format: date-time
```

Maps to:

```typescript
export type GetWidgetResponse = {
    id: string;
    status: "processing" | "completed" | "failed";
    created_at: string;
};
```

### Query parameters to input type mapping

Query parameters are merged into the input type using intersection with `PaginationParams`:

```yaml
# OpenAPI
parameters:
  - name: status
    in: query
    schema:
      type: string
  - name: limit
    in: query
    schema:
      type: string
  - name: offset
    in: query
    schema:
      type: string
```

Maps to:

```typescript
export type ListWidgetsInput = PaginationParams & {
    status?: string;
};
```

The method builds the query string with the shared `toQueryString` helper (`src/internal/query.ts`). It skips `undefined`, `null` and `""`, so an unset filter is never sent as `"undefined"`, and it returns `""` (no bare `?`) when nothing is set. Path ids are destructured out first:

```typescript
list(
    params?: ListWidgetsInput,
    options?: RequestOptions
): Promise<BlindpayApiResponse<ListWidgetsResponse>> {
    return client.get(`/instances/${instanceId}/widgets${toQueryString(params)}`, options);
},
```

`src/resources/list-query.test.ts` asserts the exact URL every list method sends. Add a case there for a new list method. The api-sync generator emits the same `toQueryString(params)` call and adds the import (`ensureQueryStringImport` in `scripts/api-sync/apply.ts`).

### Auto-pagination

Every list whose spec op accepts `starting_after` (payouts, payins, customers, payables, transfers, wallet deposits) has an auto-pager next to it: `listAutoPaging(params?, options?)` (`getDepositsAutoPaging` for deposits), returning `AsyncGenerator<Entity>`. It is one call to `autoPage()` in `src/internal/paginate.ts` with the same path as `list`; never use `this`, since resources are spread into the client. `autoPage` sends `limit` (default `"100"`), follows `pagination.next_page` as `starting_after` while `has_more`, rejects `ending_before`, stops on a bare array, throws a `BlindPayError` (with `.error`) on a failed page, and throws when the cursor doesn't advance. Add a case to `src/resources/auto-paging.test.ts` for a new pager, with hand-written pages (the shared `.b0` fixtures never stop).

### Path parameters

Every caller-supplied value interpolated into a request path is wrapped in `encodeURIComponent(...)`, so an id containing `/`, `?` or `#` can't change the route (`payouts.get("a/b")` requests `/payouts/a%2Fb`; `src/resources/path-encoding.test.ts`). `instanceId` is the exception: the client percent-encodes it once and hands the encoded value to every resource factory, so templates use `${instanceId}` as-is (upload, which sends it as a query param, gets the raw value and lets `toQueryString` encode it). api-sync's generator emits the same shape.

Path parameters that are resource IDs are handled in two ways:

1. **Single ID (the resource's own ID)**: passed as a plain string argument.
```typescript
get(id: GetWidgetInput, options?: RequestOptions): Promise<BlindpayApiResponse<GetWidgetResponse>> {
    return client.get(`/instances/${instanceId}/widgets/${encodeURIComponent(id)}`, options);
},
```

2. **Multiple IDs or ID + body**: destructured from an object input type.
```typescript
export type UpdateWidgetInput = {
    widget_id: string;
    name?: string;
};

update(
    { widget_id, ...data }: UpdateWidgetInput,
    options?: RequestOptions
): Promise<BlindpayApiResponse<SuccessResponse>> {
    return client.put(
        `/instances/${instanceId}/widgets/${encodeURIComponent(widget_id)}`,
        data,
        options
    );
},
```

3. **Nested resource IDs**: all IDs come from the input object.
```typescript
export type GetCustodialWalletInput = {
    customer_id: string;
    id: string;
};

get(
    { customer_id, id }: GetCustodialWalletInput,
    options?: RequestOptions
): Promise<BlindpayApiResponse<GetCustodialWalletResponse>> {
    const customer = encodeURIComponent(customer_id);
    return client.get(
        `/instances/${instanceId}/customers/${customer}/wallets/${encodeURIComponent(id)}`,
        options
    );
},
```

Keep the path one template literal (api-sync's coverage scan reads it as one string; never `+` pieces). Each `${...}` must stay a single expression without braces inside.

### Return type

Every method returns `Promise<BlindpayApiResponse<T>>` where `T` is the response type. `BlindpayApiResponse<T>` is a discriminated union:

```typescript
type BlindpayApiResponse<T> = { data: T; error: null } | { data: null; error: ErrorResponse }
// ErrorResponse: message, plus code, description, errors and trace_id when the API sends them
```

When the spec's 200 response is `$ref Success`, use `Promise<BlindpayApiResponse<SuccessResponse>>`. For methods with no response body, use `Promise<BlindpayApiResponse<void>>`.

### Request options (Idempotency-Key)

Every method, GETs and `/e/` routes included, takes a trailing `options?: RequestOptions` and passes it to the client as the last argument: `timeoutMs`, `headers` and `signal` apply to every call, and on POST, PUT, PATCH and DELETE `options.idempotencyKey` becomes the `Idempotency-Key` header (the API protects `POST /e/instances/{id}/tos` too, since a server SDK reaches it with the API key). `src/resources/request-options.test.ts` fails on any `client.*(...)` call that doesn't forward it, and the api-sync generator emits the same signature.

### Discriminated/variant creation

When one endpoint creates different variants based on a `type` field, create separate methods that hardcode the discriminator:

```typescript
createIndividualWithStandardKYC(
    data: CreateIndividualWithStandardKYCInput,
    options?: RequestOptions
): Promise<BlindpayApiResponse<CreateIndividualWithStandardKYCResponse>> {
    return client.post(
        `/instances/${instanceId}/customers`,
        { kyc_type: "standard", type: "individual", ...data },
        options
    );
},
```

### Object body destructuring pattern

When passing an object body to `client.post`/`client.put`, use rest destructuring even when no fields need extracting:

```typescript
create(
    { ...data }: CreateWidgetInput,
    options?: RequestOptions
): Promise<BlindpayApiResponse<CreateWidgetResponse>> {
    return client.post(`/instances/${instanceId}/widgets`, data, options);
},
```

This is the consistent pattern used throughout the codebase.

### Summary: complete checklist for adding an OpenAPI endpoint

0. First run `bun run sync -- --spec /tmp/openapi.public.json` (see "Generate before you hand-write"); if it generated the method, skip to step 7.
1. Identify the API path and HTTP method.
2. Determine which resource file it belongs to (or create a new one).
3. Define the input type from request body schema + path params.
4. Define the response type from the response schema.
5. Add the method to the factory function's return object.
6. If new resource: register in `client.ts`, re-export from `index.ts`.
7. Add tests.
8. Add a changeset.
9. Run `bun run lint:fix && bun run check-types && bun run lint:check && bun run test && bun run sync:check`.
   Always run `lint:fix` first so Biome auto-applies formatter changes
   (trailing newlines, quote style, etc.); then `lint:check` validates
   that nothing remains.
